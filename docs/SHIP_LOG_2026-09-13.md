## 1. Executive Summary

On 2026-09-13, this work hardened secrets and signing-key custody across Parmana's authorization infrastructure and closed a real, verified gap in the Paytm connector's wire protocol. Eight PRs merged across two repositories:

**AgentLabsBuildathon (Parmana core):**

- **PR #1 (docs):** ADR-0009 + a `ROADMAP.md` future-work section
- **PR #2 (code):** `Signer` abstraction — `LocalFileSigner` (default) and `KmsSigner` (AWS KMS, sign-without-release), selected by the existing `KEY_PROVIDER` config value
- **PR #3 (code):** `SecretsProvider` abstraction — `EnvSecretsProvider` (default) and `AwsSecretsManagerProvider`, wired into the HubSpot and Paytm credential providers
- **PR #4 (code):** GitHub App credential elimination via Vercel Connect, with the existing static-key path kept as a fallback
- **PR #6 (code):** Paytm connector authorization signing — `GatewayPaytmAdapter` now signs a canonical string and attaches it to every request

**parmana-paytm-agent (companion repo):**

- **PR #1 (code):** Verifies the signature PR #6 now sends, fetching Parmana's public key over HTTP and rejecting anything unsigned, expired, or tampered

**Test coverage:** 706 tests passing combined across both repos (exact per-package numbers in Section 8), zero regressions against a genuinely clean baseline.

**What this closes today, independent of AWS:** the Paytm connector's wire protocol previously accepted any request bearing the shared secret alone, with no proof Parmana's policy engine actually approved the specific `orderId`/`txnId`/`amount`. That gap is closed now — enforced in the merged code, using the local file signing key.

**What still depends on AWS, not yet true:** the signing key moving into AWS KMS (sign-without-release) and connector secrets moving into AWS Secrets Manager. Both are fully coded and unit-tested against mocks, but neither has been exercised against a real AWS account, and neither is what's actually signing/serving credentials in the merged code today (see the status banner above).

## 3. PR #2 — `Signer` Abstraction (AWS KMS sign-without-release)

**GitHub:** https://github.com/pavancharak/AgentLabsBuildathon/pull/2
**Branch:** `feat/kms-signer-abstraction`

**New files:**

- `packages/crypto/src/Signer.ts` — the interface
- `packages/crypto/src/SignerBootstrap.ts` — composition root, selects by `KEY_PROVIDER`
- `packages/crypto/src/providers/signer/LocalFileSigner.ts` — default, wraps the pre-existing `FileKeyProvider`
- `packages/crypto/src/providers/signer/KmsSigner.ts` — AWS KMS `Sign`/`GetPublicKey`/`DescribeKey`

**Modified:** all 7 pre-existing signing call sites (`VerificationCrypto`, `RefusalCrypto`, `AuditEventCrypto`, `ReceiptCrypto`, `PolicyChangeCrypto`, `ExecutionChainCrypto`, `RuntimeAuthorizationSigner`), `ArtifactSigner.ts`/`AuthorizationSigner.ts` (new `signWithSigner()` method), `packages/api/src/routes/keys.ts` (fixed a real bug — it hardcoded `new FileKeyProvider()`, bypassing bootstrap entirely), `assertSigningKeyMaterialConfigured.ts`, `server.ts`.

**What it actually does:** `KeyProvider.getPrivateKey(): Promise<KeyObject>` cannot be honestly implemented against a real KMS key (KMS never exports private material), so a parallel `Signer.sign(keyId, data): Promise<string>` interface was added, returning the same base64 signature format every existing `SignatureProvider` already produces — no format change, so verification code needed zero changes. AWS KMS added Ed25519 support in November 2025, so `KmsSigner` needs no algorithm migration from the existing `ed25519` default.

**Known gap, not yet solved:** `KmsSigner.sign(keyId, ...)` passes the application's own `keyId` string (e.g. `"default"`) straight through as KMS's `KeyId` parameter. AWS KMS accepts a key ID, full ARN, or an alias in the form `alias/<name>` there — a bare string like `"default"` will only resolve if a KMS alias is created with exactly that name (unusual — aliases are conventionally created as `alias/default`). This needs a small mapping decision (either create AWS aliases without the conventional prefix, or add a keyId→KMS-key-ID mapping in `KmsSigner`) before KMS mode can actually be turned on. Not yet decided or implemented.

**Follow-up fix (after initial push):** CI's `build-and-test` genuinely failed on first push. `SignerBootstrap` originally cached its resolved signer in a static field; `packages/api/tests/unit/supabase-caller-audit-sink.test.ts` changes `PARMANA_KEY_DIR` per test case and deletes the directory in `afterEach` — the first test to run permanently poisoned the shared cache with a directory every later test had already removed, failing 12 of that file's 13 cases. Fixed by removing the cache entirely (constructs fresh every call, matching the pre-existing per-instance behavior). The same latent pattern in `SecretsProviderBootstrap` (PR #3) was fixed proactively at the same time, before it could cause an identical failure there.

**Tests:** crypto suite baseline was 106 before this PR; final is 125 (**+19** new: the original 18 covering `LocalFileSigner`/`KmsSigner`/`SignerBootstrap`, plus 1 added by the caching-bug follow-up fix). `runtime` (77) and `api` were unaffected by this PR specifically. **Status:** merged.

## 4. PR #3 — `SecretsProvider` Abstraction (AWS Secrets Manager)

**GitHub:** https://github.com/pavancharak/AgentLabsBuildathon/pull/3
**Branch:** `feat/secrets-manager-provider`

**New files:** `packages/api/src/bootstrap/secrets/SecretsProvider.ts`, `EnvSecretsProvider.ts`, `AwsSecretsManagerProvider.ts`, `SecretsProviderBootstrap.ts`; `packages/shared/src/config/SecretsProviders.ts`.

**Modified:** `createHubSpotCredentialProvider.ts`, `createPaytmCredentialProvider.ts`, `Config.ts`/`ConfigValidation.ts` (new `PARMANA_SECRETS_PROVIDER` config value, default `"env"`), `.gitignore` (see below).

**What it actually covers — and doesn't:** wires **only HubSpot and Paytm** connector credentials through the abstraction. GitHub is handled entirely separately (PR #4, Vercel Connect — not Secrets Manager at all). Supabase was in ADR-0009's original scope description but turned out to have **zero production call sites** — the `supabase-js` client `SUPABASE_SERVICE_ROLE_KEY` was for was deleted 2026-09-09 (`createCallerAuditSink.ts`'s own comment documents this). The actual live secret, `DATABASE_URL`, is consumed synchronously across multiple `PostgresPoolFactory.create()` call sites in `@parmana/storage`; routing that through `SecretsProvider` would require making that factory (and every caller) async — a larger, separate, still-undone piece of work.

**How switching modes actually works:** `PARMANA_SECRETS_PROVIDER` is one global switch for every connector at once — there's no per-connector mode today. In `env` mode (default), `HUBSPOT_PRIVATE_APP_TOKEN`/`PAYTM_CONNECTOR_SHARED_SECRET` hold the real credential directly, unchanged from before this PR. In `aws-secrets-manager` mode, those same env vars instead hold the _name_ of a Secrets Manager secret to fetch — there is no hardcoded secret-name convention in the code; whatever name you create the secret under is whatever you set the env var to.

**Also fixed:** `.gitignore`'s `*secret*` rule was silently swallowing entire new source directories by path (and, in PR #1, the ADR file itself, purely by filename). Added scoped negations for `src`/`tests`/`docs` paths; `gitleaks` (content-based scanning) remains the real backstop and still catches genuine stray secret-shaped files everywhere else.

**Tests:** 10 new (`EnvSecretsProvider`, `AwsSecretsManagerProvider` against a fully mocked `@aws-sdk/client-secrets-manager`, `SecretsProviderBootstrap` provider selection). `api` baseline (true, clean-rebuild-verified) was 242 passed/66 failed/342 total before this PR. **Status:** merged.

## 6. PR #6 — Paytm Connector Authorization Signing (Parmana side)

**GitHub:** https://github.com/pavancharak/AgentLabsBuildathon/pull/6
**Branch:** `feat/paytm-signature-verification`

**Modified/new:**

- `packages/connector-paytm/src/PaytmTypes.ts` — adds `canonicalPaytmAuthorizationString()` and `PAYTM_AUTHORIZATION_SIGNATURE_TTL_MS`
- `packages/connector-paytm/src/MockPaytmConnectorServer.ts` — this repo's hermetic stand-in for the real `parmana-paytm-agent` service now verifies the signature too, so this repo's own test suite exercises the real security property
- `packages/execution-gateway/src/connector-execution/GatewayPaytmAdapter.ts` — signs and attaches the authorization

**What it actually does — precisely, not the JWT/proofChain version an earlier draft of this document incorrectly described:**

`canonicalPaytmAuthorizationString()` builds a **plain pipe-delimited string** — `businessTransactionId|action|orderId|txnId|amount|expiresAt` — not a JWT, not JSON. Pipe-delimited specifically because this string crosses a repo boundary maintained by two independently-evolving codebases, and JSON key ordering isn't a contract either side can rely on staying identical. `GatewayPaytmAdapter` computes `expiresAt = Date.now() + PAYTM_AUTHORIZATION_SIGNATURE_TTL_MS`, where **the TTL is 60 seconds (`60_000`), not five minutes**. It signs the string via `SignerBootstrap.create()` — today that resolves to `LocalFileSigner` (the local file key), since `KEY_PROVIDER=aws-kms` isn't configured anywhere yet — and attaches `signature` (base64), `keyId`, and `expiresAt` to the outbound `authorization` object.

**Tests:** `connector-paytm` baseline was 32 before this PR, final 36 (**+4**, locking down `canonicalPaytmAuthorizationString`'s exact format and the TTL bound — regression protection against silent cross-repo drift). `execution-gateway` baseline was 132, final 136 (**+4**: a signed request is independently verifiable end-to-end; a missing signature is rejected; an expired-but-genuinely-signed signature is rejected; a tampered amount is rejected even with a valid signature over a _different_ amount — proving the shared secret alone is no longer sufficient to forge a refund).

**Status:** merged.

## 7. parmana-paytm-agent PR #1 — Signature Verification (companion, separate repo)

**GitHub:** https://github.com/pavancharak/parmana-paytm-agent/pull/1

**New files:** `src/parmana/keys.ts` (fetches Parmana's public key). **Modified:** `src/parmana/authorization.ts` (adds `canonicalPaytmAuthorizationString()` — a byte-for-byte copy of the Parmana-side function of the same name — and `verifyPaytmAuthorizationSignature()`), `src/server/handler.ts` (`executeAuthorizedConnectorRequest`, exported so it's directly unit-testable, calls the verification after existing parameter parsing and before ever calling `connector.initiateRefund()`).

**What it actually does:** fetches Parmana's public key via **`GET /keys/:keyId`** — a specific key lookup, deliberately unauthenticated (no `PARMANA_API_KEY` sent, matching that endpoint's own design in the Parmana repo, which mounts it ahead of caller-auth specifically so a third party can verify without a credential). This is **not** the `.well-known/jwks.json` listing endpoint an earlier draft of this document incorrectly named. Rebuilds the identical canonical string, verifies with Node's built-in `crypto.verify()`, and rejects if `Date.now()` has passed `expiresAt`. Every validation failure — missing signature, expired, invalid — is a plain thrown `Error`, uniformly surfaced as HTTP 500 by the existing outer request handler; there's no special status code carved out for signature failures specifically, matching this file's own pre-existing convention for every other validation failure.

**Tests:** repo baseline was 21 before this PR, final 37 (**+16**: 5 for `fetchParmanaPublicKey`, 6 for the canonicalization/verification functions, 5 for `executeAuthorizedConnectorRequest` end-to-end — including the exact scenario this fix closes, a self-chosen amount with no valid signature, which previously would have been honored and now is rejected). `tsc --noEmit` and `eslint` both clean.

**Status:** merged.

## 9. Phase 2B: Paytm Wire-Protocol Signature Verification — Status

**Code status:** merged and enforced, both repos, right now — this is not "ready to use once AWS is provisioned" the way PRs #2/#3 are. The signature check runs on every request today.

**What is and isn't true today:**

- ✅ Every `POST /connector/paytm-refund` request must carry a valid signature over its own exact `businessTransactionId`/`orderId`/`txnId`/`amount`, or it's rejected.
- ✅ The signature has a 60-second expiry, bounding replay of a captured request.
- ⚠️ The signing key used right now is the **local file key** (`KEY_PROVIDER` defaults to `local`), not an AWS KMS key — because AWS isn't provisioned. The verification is genuinely enforced; the specific key backing it isn't yet the hardened one PR #2 makes possible.

**Security impact:** closes the "attacker with the Paytm shared secret alone can forge any refund transaction" gap completely, independent of AWS. Once `KEY_PROVIDER=aws-kms` is actually configured (blocked on the KMS-alias gap noted in Section 3 and AWS provisioning generally), the same enforcement additionally gets sign-without-release custody of the key itself.

## 13A. Secrets Provisioning Checklist (AWS Activation Phase)

Once AWS account verification completes, only two connector secrets need provisioning — **not three**: Supabase is deliberately excluded (Section 4 explains why; `SUPABASE_SERVICE_ROLE_KEY` has no production call site in this codebase). GitHub is also excluded here — it's handled by Vercel Connect (PR #4), not Secrets Manager.

**Important — the secret value must be the raw credential string, not a JSON object.** `AwsSecretsManagerProvider.getSecret()` (`packages/api/src/bootstrap/secrets/AwsSecretsManagerProvider.ts`) reads `SecretString` and returns it **as-is, with no JSON parsing** — whatever you store is exactly what gets sent to HubSpot/Paytm as the credential. Storing `{"HUBSPOT_PRIVATE_APP_TOKEN":"pat-..."}` would send that literal JSON string as the bearer token and break authentication.

**The secret's name is also not fixed by the code.** Pick any name; whatever you choose, set the corresponding env var (`HUBSPOT_PRIVATE_APP_TOKEN` or `PAYTM_CONNECTOR_SHARED_SECRET`) to that same name once `PARMANA_SECRETS_PROVIDER=aws-secrets-manager` is set. The names below are a suggested convention, not a requirement.

### HubSpot

```bash
aws secretsmanager create-secret \
  --name parmana/hubspot-private-app-token \
  --secret-string '<the-actual-pat-... token, nothing else>' \
  --region <your-chosen-region>
```

Then set `HUBSPOT_PRIVATE_APP_TOKEN=parmana/hubspot-private-app-token` and `PARMANA_SECRETS_PROVIDER=aws-secrets-manager` in Vercel's environment variables.

**Status:** not yet provisioned (awaits AWS account verification).

### Paytm

```bash
aws secretsmanager create-secret \
  --name parmana/paytm-connector-shared-secret \
  --secret-string '<the-actual-shared-secret, nothing else>' \
  --region <your-chosen-region>
```

Then set `PAYTM_CONNECTOR_SHARED_SECRET=parmana/paytm-connector-shared-secret`.

**Status:** not yet provisioned (awaits AWS account verification).

### Verification

```bash
aws secretsmanager list-secrets --region <your-chosen-region> --filters Key=name,Values=parmana/
aws secretsmanager get-secret-value --secret-id parmana/hubspot-private-app-token --region <your-chosen-region>
aws secretsmanager get-secret-value --secret-id parmana/paytm-connector-shared-secret --region <your-chosen-region>
```

Then deploy to staging with `PARMANA_SECRETS_PROVIDER=aws-secrets-manager` set and confirm both connectors still authenticate successfully — this exact path has only been tested against a mocked AWS SDK client so far, never a real Secrets Manager instance.

### While waiting for AWS verification

Do not put these two credentials anywhere new. The code already reads them from wherever they are today (`.env`, in `env` mode) unchanged. Useful prep during the wait:

```
Credential location tracker (fill in before starting provisioning):
```
