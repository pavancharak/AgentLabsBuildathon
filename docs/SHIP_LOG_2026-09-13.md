# Ship Log — 2026-09-13: Secrets & Signing-Key Custody Hardening

> **Status:** 4 PRs open for review, 0 merged. Phase 2B (Paytm protocol signature fix) not started.
> **Security impact:** Removes the gateway's private signing key and connector credentials from `.env`/process memory as the sole point of trust; the deepest gap found (Paytm connector wire-protocol bypass) remains open until Phase 2B ships.
> **Cost:** Rough estimate only, not a verified bill — see [Section 6](#6-cost-estimate-unverified).
> **Timeline:** Illustrative, not committed — see [Section 7](#7-illustrative-sequence-not-a-committed-schedule).

## 1. Executive Summary

- **Date:** 2026-09-13
- **Scope:** Secrets and signing-key custody hardening, per [ADR-0009](adr/ADR-0009-KMS-Secrets-And-Connector-Signature-Hardening.md).
- **Trigger:** A code-level audit (reading `process.env` call sites and the actual connector wire protocol, not documentation) found the gateway's Ed25519 signing key readable via `.env`/local disk, connector secrets as plain environment reads, and — separately, and more seriously — the Paytm connector's wire protocol accepting an unsigned authorization payload, checked only by a shared bearer secret.
- **Shipped today:** 4 pull requests, all open, none merged.
- **Not shipped:** The Paytm wire-protocol signature fix (Phase 2B) — the change that closes the most serious of the four findings. It requires coordinated changes across this repo and the separate `parmana-paytm-agent` repo and has not been started.

### PR #2 — AWS KMS Signer Abstraction
**Branch:** `feat/kms-signer-abstraction` · **Link:** [PR #2](https://github.com/pavancharak/AgentLabsBuildathon/pull/2)

- **New files:** `packages/crypto/src/Signer.ts`, `SignerBootstrap.ts`, `providers/signer/LocalFileSigner.ts`, `providers/signer/KmsSigner.ts`.
- **Modified:** All 7 signing call sites (`VerificationCrypto`, `RefusalCrypto`, `AuditEventCrypto`, `ReceiptCrypto`, `PolicyChangeCrypto`, `ExecutionChainCrypto`, `RuntimeAuthorizationSigner`), plus `ArtifactSigner.ts`/`AuthorizationSigner.ts` (new `signWithSigner()` method), `packages/api/src/routes/keys.ts` (fixed a bug: it hardcoded `new FileKeyProvider()` directly, bypassing bootstrap entirely), `assertSigningKeyMaterialConfigured.ts`, `server.ts`.
- **What it does:** AWS KMS supports Ed25519 asymmetric signing keys (added Nov 2025) — no algorithm migration needed. `KmsSigner` calls KMS's `Sign`/`GetPublicKey`/`DescribeKey` APIs only; the private key material never leaves KMS, even if the Parmana process itself is fully compromised. This required more than swapping a config value: `KeyProvider.getPrivateKey(): Promise<KeyObject>` cannot be honestly implemented against a real KMS key (KMS never exports private material), so a parallel `Signer.sign(keyId, data)` interface was added and all 7 call sites migrated onto it.
- **Why it matters:** Closes the highest-value finding — the key that signs every Execution Authorization, Trust Record, Refusal Record, and Attestation this system produces no longer sits on disk or in a process-readable env var when `KEY_PROVIDER=aws-kms` is configured.
- **Tests:** 18 new unit tests (`LocalFileSigner` — byte-identical to prior behavior, verified; `KmsSigner` against a fully mocked `@aws-sdk/client-kms`, no real AWS calls; `SignerBootstrap` provider selection).
- **Follow-up fix (post-push):** CI's `build-and-test` job genuinely failed on the first push — `SignerBootstrap` originally cached its result in a static field, unlike every prior call site's own fresh-`FileKeyProvider()`-per-instance behavior. `packages/api/tests/unit/supabase-caller-audit-sink.test.ts` changes `PARMANA_KEY_DIR` per test and tears the directory down in `afterEach`; the first test to run permanently poisoned the process-wide cached signer with an already-deleted directory, failing 12 of that file's 13 tests. Fixed: `SignerBootstrap.create()` no longer caches, constructs fresh every call. Pushed as a follow-up commit; CI now green.
- **Regression check:** Full `crypto` (125 tests) and `runtime` (77 tests) suites pass. `api` suite: 242 passed, 66 pre-existing unrelated failures — see the correction note in [Section 3](#3-test-coverage-summary) for why this number differs from what was first claimed here.

### PR #3 — AWS Secrets Manager for Connector Credentials
**Branch:** `feat/secrets-manager-provider` · **Link:** [PR #3](https://github.com/pavancharak/AgentLabsBuildathon/pull/3)

- **New files:** `packages/api/src/bootstrap/secrets/SecretsProvider.ts`, `EnvSecretsProvider.ts`, `AwsSecretsManagerProvider.ts`, `SecretsProviderBootstrap.ts`, `packages/shared/src/config/SecretsProviders.ts`.
- **Modified:** `createHubSpotCredentialProvider.ts`, `createPaytmCredentialProvider.ts`, `Config.ts`/`ConfigValidation.ts` (new `PARMANA_SECRETS_PROVIDER` config value), `.gitignore`.
- **What it does:** `HUBSPOT_PRIVATE_APP_TOKEN` and `PAYTM_CONNECTOR_SHARED_SECRET` route through a new `SecretsProvider` abstraction. In the default `env` mode, behavior is unchanged (identity pass-through). In `aws-secrets-manager` mode, the same env var instead holds the Secrets Manager secret name/ARN.
- **Scope correction made during this work:** ADR-0009 originally described this as covering "HubSpot/Paytm/Supabase" secrets. `SUPABASE_SERVICE_ROLE_KEY` turned out to have **zero production call sites** — the `supabase-js` client it was for was deleted 2026-09-09 (per `createCallerAuditSink.ts`'s own comment). The actual live secret is `DATABASE_URL`, consumed synchronously across multiple `PostgresPoolFactory.create()` call sites in `@parmana/storage` — routing that through `SecretsProvider` would require making that factory (and every caller) async, a separate, larger change explicitly deferred rather than forced into this PR.
- **Also fixed:** `.gitignore`'s `*secret*` rule was silently swallowing entire new source directories (and, in PR #1, the ADR file itself) purely because "secrets" appears in the path. Added scoped negations for `src`/`tests`/`docs` paths; `gitleaks` (content-based scanning) remains the actual backstop and still catches genuine stray secret-shaped files elsewhere — verified both directions.
- **Tests:** 10 new unit tests (`EnvSecretsProvider`, `AwsSecretsManagerProvider` against a fully mocked `@aws-sdk/client-secrets-manager`, `SecretsProviderBootstrap` provider selection).
- **Follow-up fix (post-push, proactive):** `SecretsProviderBootstrap` had the identical static-caching pattern that broke PR #2 (above). No test in this suite currently toggles `AWS_REGION`/`AWS_ROLE_ARN` between cases, so it wasn't visibly failing here, but fixed proactively rather than waiting for it to bite: `SecretsProviderBootstrap.create()` no longer caches.
- **Regression check:** `shared` suite 40/40. `api` suite: 252 passed, 66 pre-existing unrelated failures (see [Section 3](#3-test-coverage-summary)'s correction note).

### PR #4 — GitHub Credential via Vercel Connect
**Branch:** `feat/vercel-connect-github-credential` · **Commit:** `8743814` · **Link:** [PR #4](https://github.com/pavancharak/AgentLabsBuildathon/pull/4)

- **Modified:** `createGitHubCredentialProvider.ts`, plus a new test file.
- **What it does:** Unlike PRs #2 and #3, this doesn't relocate a secret — it removes `GITHUB_APP_ID`/`GITHUB_INSTALLATION_ID`/`GITHUB_APP_PRIVATE_KEY` from the process environment entirely, for a deployment that sets `PARMANA_GITHUB_VERCEL_CONNECT_CONNECTOR_ID`. Vercel Connect owns the GitHub App registration and mints installation tokens on demand (`@vercel/connect`'s `getToken()`); this process never holds the App's private key. The existing `GITHUB_APP_*` env-var path is kept as a fallback, not removed, for a deployment not using Vercel Connect; the `NODE_ENV=test` hermetic path is untouched.
- **Why it matters:** The GitHub connector's "ephemeral credential" design claim previously only covered the *installation token* — the App's private key itself was still a static, unrotated env var. This closes that specific gap.
- **Tests:** 3 new unit tests (Vercel Connect path mints a token with the correct connector id/subject; `resolve()` rejects a non-`github` connectorId; fallback path when the Connect env var is unset).
- **Regression check:** `api` suite: 245 passed, 66 pre-existing unrelated failures. This branch's own code has no bug — its first check showed a misleading 140-failure count from a stale `dist/` build mismatch across packages, resolved with a clean rebuild (see [Section 3](#3-test-coverage-summary)).

## 4. Security Improvements by PR

| PR | Before | After |
|---|---|---|
| #2 KMS Signer | Gateway's Ed25519 private key readable from `.env` (`PARMANA_KEY_MATERIAL_JSON`) or local disk (`./keys/*.private.pem`) by anything with the process's filesystem access. | With `KEY_PROVIDER=aws-kms`: private key material never leaves AWS KMS. A compromised process can request signatures but cannot exfiltrate the key itself. |
| #3 Secrets Manager | `HUBSPOT_PRIVATE_APP_TOKEN`/`PAYTM_CONNECTOR_SHARED_SECRET` as static, unrotated plaintext env vars. | With `PARMANA_SECRETS_PROVIDER=aws-secrets-manager`: same env vars hold a Secrets Manager reference instead of the raw value; AWS CloudTrail logs every access. |
| #4 Vercel Connect | GitHub App's private key a static env var, valid indefinitely. | With Vercel Connect configured: no App private key in this process at all; installation tokens are short-lived and minted per use. |

**What none of the above changes:** the Paytm connector's wire protocol (see Section 5) still accepts any request bearing the shared secret, with no cryptographic proof that Parmana's policy engine actually approved it. Moving that secret to Secrets Manager (PR #3) does not close this — it is a protocol gap, not a secrets-at-rest gap, and is unaffected by anything shipped today.

## 5. What's Not Shipped Yet

**Phase 2B — Paytm connector wire-protocol signature verification.** Not started.

Traced during this work: `GatewayPaytmAdapter.ts` (this repo) sends an unsigned JSON `authorization.payload` to the remote `parmana-paytm-agent` service; that service's `executeAuthorizedConnectorRequest` (`src/server/handler.ts`) verifies only a bearer shared secret and a string match on `businessTransactionId` — never a cryptographic signature. Anyone holding `PAYTM_CONNECTOR_SHARED_SECRET` can call `POST /connector/paytm-refund` directly with self-chosen parameters, bypassing Parmana's policy engine, rate limits, and spend caps entirely.

The designed fix (in ADR-0009 §4): `GatewayPaytmAdapter` signs a canonical payload with the same gateway key from PR #2; `parmana-paytm-agent` fetches Parmana's public key via the existing `GET /keys/:keyId` endpoint and verifies it before executing. This spans two independently deployed repositories and has not been implemented — no code exists for it yet in either repo.

Not a bill, not confirmed against a provisioned account — a rough figure from published AWS list pricing for the resources described in ADR-0009 (one KMS asymmetric key, two Secrets Manager secrets), at low request volume:

**Rough total: ~$2/month.** Treat this as an order-of-magnitude estimate, not a commitment — nothing has actually been provisioned yet (see open decisions below), and Vercel Connect's own pricing (for the GitHub App path in PR #4) was not modeled here.

## 8. Open Decisions

### AWS Account Verification Failed

**Blocker:** Aadhaar identity verification failed during account signup.

**What happened:** During AWS account creation, the identity verification step rejected the Aadhaar details (mismatch between entered name and Aadhaar record, or verification method issue).

**Impact:** Cannot provision KMS asymmetric key or Secrets Manager secrets until AWS account is fully activated and verified.

**Workaround:** All Phase 1 documentation (ADR-0009, ROADMAP.md) is complete and independent of AWS provisioning. Can be reviewed and merged while AWS verification is being retried.

**Next step:** Retry identity verification in AWS console:
1. Go to https://console.aws.amazon.com/billing/home
2. Click "Account" (left menu)
3. Click "Verify your identity" under verification status
4. Re-enter details (ensure name matches Aadhaar exactly)
5. Complete OTP verification
6. Once verified (status shows green checkmark), proceed to provision KMS/Secrets Manager

**Timeline impact:** Adds 1-2 days. All 4 PRs can be reviewed and merged in parallel while AWS verification is being retried.

## 9. Summary for External Readers

What can be said with confidence, based on what actually shipped and was verified today: four pull requests are open (none merged) that move the gateway's signing key toward AWS KMS custody (sign-without-release), move two connector credentials toward AWS Secrets Manager, and eliminate the GitHub App's static private key via Vercel Connect — each with unit test coverage and confirmed zero regressions against the true, properly-verified baseline (66 pre-existing unrelated failures, corrected from an initially-miscounted 78 — see Section 3). That miscount led to catching and fixing one genuine CI failure (a caching bug in `SignerBootstrap` that broke test isolation) and one proactive fix of the same pattern elsewhere, both before merge. None of this is deployed; none of the AWS infrastructure it depends on has been provisioned. The most serious individual finding from the audit that started this work — the Paytm connector's wire protocol accepting unsigned authorization payloads — remains open and unaddressed.
