\# Execution Receipt

\## Purpose

This document defines the \*\*Execution Receipt (ER)\*\*, the portable proof generated by Parmana after an Authorization Decision has been recorded.

An Execution Receipt provides verifiable evidence that an Execution Request was evaluated and that an Authorization Decision was produced.

Unlike the Execution Trust Record, which is the canonical internal authorization record, the Execution Receipt is intended to be shared with external systems, execution systems, operators, auditors, and downstream services.

This document is normative.

\---

\# Definition

An \*\*Execution Receipt (ER)\*\* is a cryptographically verifiable representation of an Authorization Decision.

It is generated from an Execution Trust Record.

An Execution Receipt allows another system to verify that Parmana authorized a Business Transaction without requiring direct access to the internal Runtime.

\---

\# Purpose

The Execution Receipt exists to provide portable proof of authorization.

It enables external systems to answer questions such as:

\* Was this action authorized?

\* Which policy governed the authorization?

\* What was the authorization outcome?

\* Can the authorization be independently verified?

\* Has the receipt been modified?

The Execution Receipt provides this information without exposing the complete internal authorization record.

\---

\# Core Principle

The Execution Receipt is \*\*derived evidence\*\*.

It is not the source of truth.

The source of truth is the Execution Trust Record.

```text

Execution Trust Record

&#x20;       │

&#x20;       ▼

Execution Receipt

```

The receipt summarizes and proves the authorization represented by the Execution Trust Record.

\# Responsibilities

The Execution Receipt is responsible for:

\* Proving authorization.

\* Identifying the Authorization Decision.

\* Identifying the governing policy.

\* Preserving integrity.

\* Supporting independent verification.

\* Enabling trusted communication between systems.

\---

\# Logical Structure

Conceptually, an Execution Receipt contains:

```text

Execution Receipt

├── Receipt Identifier

├── Execution Trust Record Reference

├── Authorization Decision

├── Policy Reference

├── Policy Version

├── Receipt Timestamp

├── Integrity Hash

├── Digital Signature

└── Receipt Metadata

```

The exact serialization format is implementation-specific.

\---

\# Relationship to the Execution Trust Record

Every Execution Receipt is derived from exactly one Execution Trust Record.

```text

Execution Trust Record

&#x20;       │

&#x20;       ▼

Execution Receipt

```

The receipt contains only the information necessary to verify authorization.

The complete authorization evidence remains inside the Execution Trust Record.

\---

\# Relationship to Authorization Decision

Every Execution Receipt records the Authorization Decision.

Examples include:

\* Approved

\* Rejected

\* Awaiting Approval

\* Escalated

Execution systems use the recorded outcome to determine whether execution may proceed.

\---

\# Relationship to Policy

The Execution Receipt identifies the governing policy.

This allows downstream systems to understand the authorization context and supports independent verification.

The receipt references the policy but does not embed the complete policy definition.

\---

\# Relationship to Cryptography

Execution Receipts are protected using cryptographic integrity mechanisms.

Typical integrity information includes:

\* Hash

\* Digital signature

\* Algorithm identifier

These mechanisms allow any verifier to detect unauthorized modification.

Cryptographic implementation details are specified in `CRYPTOGRAPHY.md`.

\---

\# Receipt Verification

Receipt verification confirms:

\* the receipt has not been modified,

\* the receipt was issued by Parmana,

\* the referenced authorization exists,

\* the receipt corresponds to the recorded Authorization Decision.

Receipt verification does not require trusting the requesting AI system.

\---

\# Receipt Consumers

Execution Receipts may be consumed by:

\* Enterprise applications

\* AI agents

\* Workflow engines

\* API gateways

\* ERP systems

\* Financial systems

\* Audit systems

\* Compliance platforms

Each consumer receives the same portable proof of authorization.

\---

\# Minimal Disclosure

Execution Receipts should disclose only the information required for verification.

Sensitive authorization evidence remains within the Execution Trust Record.

This minimizes information exposure while preserving trust.

\---

\# Immutability

Once generated, an Execution Receipt MUST NOT be modified.

If a new Authorization Decision is produced, a new Execution Receipt MUST also be generated.

Historical receipts remain valid representations of the original authorization.

\---

\# Security Considerations

Execution Receipts must protect against:

\* forgery,

\* tampering,

\* substitution,

\* unauthorized modification,

\* replay attacks.

Integrity protection is mandatory.

\---

\# Design Principles

Execution Receipts follow these principles:

\* Portable.

\* Verifiable.

\* Immutable.

\* Cryptographically protected.

\* Derived from the Execution Trust Record.

\* Suitable for machine verification.

\* Suitable for human inspection.

\---

\# What an Execution Receipt Is Not

An Execution Receipt is \*\*not\*\*:

\* an Execution Request,

\* an Organizational Policy,

\* an Execution Trust Record,

\* an audit log,

\* a workflow definition,

\* an AI response,

\* a database record.

It is a portable proof that authorization occurred.

\---

\# Guarantees

Parmana provides the following guarantees:

\* Every Execution Receipt is derived from exactly one Execution Trust Record.

\* Every Execution Receipt represents exactly one Authorization Decision.

\* Every Execution Receipt is immutable.

\* Every Execution Receipt can be independently verified.

\* Any unauthorized modification can be detected.

\* A receipt never replaces the canonical Execution Trust Record.

\# Summary

The Execution Receipt provides independently verifiable proof that Parmana evaluated an Execution Request and produced an Authorization Decision.

Derived from the Execution Trust Record and protected through cryptographic integrity mechanisms, it enables execution systems, enterprise applications, auditors, and external services to verify authorization without requiring direct access to Parmana's internal records.

The Execution Trust Record remains the canonical source of truth. The Execution Receipt is the portable proof of that truth.
