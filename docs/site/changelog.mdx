Parmana ships continuously, there's no separate server release train with its own version
numbers (the running server's `GET /version` reports an internal build identifier, not a
product version). The SDKs are versioned independently on their own registries, see
[TypeScript SDK](/sdks/typescript) and [Python SDK](/sdks/python) for their current versions
and per-version notes. This page covers changes that affect what you can build against, not
every commit, run `git log` in the repository for the complete record.

## 2026-09-25

**Added**

- **Self hosted deployment.** `docker compose up -d --build --wait` runs Parmana and its own Postgres on your infrastructure, with signing keys, API keys, migrations and policies handled, and nothing sent to Parmana. See [Self hosted Parmana](/self-hosted/overview) and the [quickstart](/self-hosted/quickstart).
- **Offline verification.** `bash docker/local/offline-check/run.sh` proves, on a network with no internet route, that policy approval, an authorized and a refused decision, and Trust Record verification with only the public keys all work. See [Offline verification](/self-hosted/offline-verification).
- `PARMANA_STORAGE=postgres`. It selects the same Postgres storage as `supabase`, which is unchanged. See the [environment variable reference](/deployment/environment-variables#storage).

**SDK 1.3.0, published on npm and PyPI**

Both SDKs now cover the same operations. Both were published on 2026-09-25: `npm install @parmana/sdk` and `pip install parmana` install 1.3.0. See [SDK coverage of the API](/sdks/api-coverage).

- Policy governance in both SDKs: propose, list for review, approve and reject a policy change, and sign the step up authorization on the approver's machine (`signPolicyChangeStepUp()`, `parmana.crypto.sign_policy_change_step_up()`). An approver no longer needs a clone of the repository.
- `caller()` (`GET /callers/me`), `publicKey()` / `public_key()` (`GET /keys/{keyId}`) and Trust Record listing (`GET /trust-records`) in both SDKs.
- TypeScript: offline verification of Trust Records and Execution Intents (`verifyExecutionTrustRecordOffline`, `verifyExecutionIntentOffline`), which only the Python SDK had; `latestReceipt()`; and `statusCode` on every HTTP error, which only the Python SDK had (`status_code`).
- Python: the offline verifiers also accept the SDK's own models, so `client.execution_intent(id).intent` can be passed directly; `latest_receipt()` shortcut.

**Corrected**

- `scripts/apply-all-migrations.sql` is safe to run once on an empty database, and **not** safe to run again on a database that holds data. The docs used to say otherwise. For an existing database, apply only the migration files it does not have yet.

## 2026-09-21

**Added**

- **Execution Intents.** Before an action is released to a connector, the runtime now signs and stores a record of
  exactly what it is about to release. If that cannot be done, nothing is released and the caller gets
  `503 EXECUTION_INTENT_UNAVAILABLE`. This closes the ordering gap recorded as G-52 and makes the missing record
  recorded as G-53 repairable. See [Execution Intents](/concepts/execution-intents).
- Four routes: `POST /execution-intents/verify` (no credential needed), `GET /execution-intents/{businessTransactionId}`,
  `GET /execution-intents/unfinalized` and `POST /execution-intents/{businessTransactionId}/finalize`. The last two need a
  credential provisioned as a verified human. Finalize rebuilds a missing Execution Trust Record for a released action
  without calling the connector, and is safe to run twice.
- A fifth route, `POST /execution-intents/{businessTransactionId}/resolve`, lets a verified human close an intent in state `PREPARED` or `ERRORED` after reconciling it at the connector. It records what they found (`NOT_EXECUTED` or `EXECUTED`), a required note, who did it and when, and takes the intent out of the unfinalized list. It is idempotent and never calls a connector. The resolution is an attributed operator statement in unsigned status. It is not tamper evident and it is not a Trust Record.
- `scripts/verify-execution-intent.ts` verifies an intent offline with only the public key.
- New error codes: `EXECUTION_INTENT_UNAVAILABLE` (503), `EXECUTION_INTENT_NOT_FOUND` (404),
  `EXECUTION_INTENT_RESULT_NOT_RECORDED` (409) `EXECUTION_INTENTS_NOT_ENABLED` (501), `EXECUTION_INTENT_NOT_RESOLVABLE` (409) and `EXECUTION_INTENT_RESOLUTION_INVALID` (400). See the
  [error catalog](/api-reference/error-catalog).
- The environment variable `EXECUTION_INTENTS_CHECK`, which only has an effect in `test` and `development`.

**Changed, and needs action before you deploy**

- Execution Intents are enforced by default and cannot be switched off in production. **Apply
  `supabase/migrations/20260921120000_add_execution_intents.sql` before you deploy this version.** Without the table,
  every execution is refused with `503 EXECUTION_INTENT_UNAVAILABLE`. The migration only adds a table and is safe to run
  twice.
- `GET /ready` now also checks that the `execution_intents` table exists, and returns `503` with `NOT_READY` and the
  migration file name when it does not.
- `EXECUTION_RECORD_INCOMPLETE` is no longer a dead end. The signed intent exists, and an operator can rebuild the
  record with `POST /execution-intents/{businessTransactionId}/finalize` when the intent is in state `RELEASED`.
- Each released action now costs one more signing operation and three more database writes. Under AWS KMS that is one
  more `kms:Sign`, about 35 ms in the one measurement made, from a Windows machine to `ap-south-1`.

**Known limits**

- A resolution is not tamper evident and does not create a Trust Record. For an action that ran and has no Trust
  Record, the signed intent, the operator's note and the connector's own record are the evidence.

- The SDK methods for the Execution Intent routes are available from SDK 1.2.0, published on 2026-09-21. Earlier versions do not have them. The TypeScript SDK has no offline intent verifier.

**Added to the SDKs (version 1.2.0 for both, published on 2026-09-21)**

- TypeScript `ParmanaClient`: `executionIntent`, `verifyExecutionIntent`, `unfinalizedExecutionIntents`, `finalizeExecutionIntent`, `resolveExecutionIntent`, with the `ExecutionIntentApi` class and its types.
- Python `ParmanaClient`: `execution_intent`, `verify_execution_intent`, `unfinalized_execution_intents`, `finalize_execution_intent`, `resolve_execution_intent`, with `ExecutionIntentApi`, the intent models, and `parmana.crypto.verify_execution_intent_offline`, an offline verifier that needs only the public key.

**Fixed**

- The JSON schema `$id` values under `schemas/` used the domain `schemas.parmana.ai`. They now use
  `schemas.parmanasystems.com`. They are identifiers only and no route or response changed.

## 2026-09-20

**Changed**

- The Execution Gateway now fails closed on policy binding. An authorization with no
  `policyContentHash`, a policy that has no signed approval record, a policy whose live content
  differs from its approved content, or an error from the approval check all reject the request
  before the connector runs. Authorizations signed before `policyContentHash` existed are now
  rejected instead of skipped, so re-authorize any in flight request.
- Execution time policy governance verification is now on by default. It is relaxed only when
  `NODE_ENV` is `test` or `development`, and `POLICY_EXECUTION_VERIFICATION_ENFORCED` can no
  longer switch it off in production. Every policy you execute against needs a signed approval
  record before you promote a deployment.
- `ExecutionGateway` requires a `policyRepository` and a `policyApprovalVerifier` at
  construction. Tests and examples that predate this can set `allowUnverifiedPolicy: true`,
  which production must not use. `GatewayVerificationResult` gains
  `checks.policyGovernanceVerified` and `policyGovernanceViolation`.

**Fixed**

- Signing a full Execution Trust Record under AWS KMS failed with `Member must have length less than
or equal to 4096`, because KMS refuses a raw Ed25519 message over 4096 bytes. A message over that
  size is now signed as a fixed 97 byte commitment (a prefix, a NUL byte, and the SHA-512 digest), and
  verifiers accept it. Signatures issued before this change are unaffected. A verifier you wrote
  yourself must implement the same rule to verify large KMS signed records, see the
  [large message rule](/guides/verify-independently). The Python SDK's offline verifier accepts the commitment form. That fix ships in Python SDK 1.1.5, published to PyPI on 2026-09-20.
- The Python SDK now declares the `cryptography` package that `parmana.crypto` (the offline Trust Record
  verifier) imports. It is an optional extra, `pip install "parmana[verify]"`, and is included in the `dev`
  extra. It was previously imported but undeclared, which made the `Python SDK` CI check fail on `mypy`.
- The runtime now proves the evidence signing path works before it releases an action. If signing
  is unhealthy the request is refused with `503 SIGNING_UNAVAILABLE` and nothing is executed. If the
  action was released and the signed record then cannot be produced or persisted, the response is
  `500 EXECUTION_RECORD_INCOMPLETE` with the `businessTransactionId` and `authorizationId`, and you must
  reconcile instead of retrying as a new transaction. Enforced everywhere except `NODE_ENV` `test` and
  `development`. The startup log gains `signingReadinessConfigured`. This mitigates the ordering gap G-52
  and does not close it.
- New page [AWS KMS signing](/deployment/aws-kms-signing): create the key, the Vercel role and policy, the environment, and how to verify. Adds `npm run verify:kms` (`scripts/verify-kms-signing.ts`), which signs test data through the repository's own `KmsSigner` on both sides of the 4096 byte KMS limit and requires KMS to refuse a raw message over it. Verified on 2026-09-20 against the real key with a limited IAM user, and end to end with the server signing a full Trust Record under KMS. Pages that said KMS was roadmap or not built (Cryptography, FAQ, Local deployment, Deploy patterns) are corrected. Azure Key Vault, Google Cloud KMS and HSM remain unimplemented.
- An approved action whose connector is not configured now returns `503` with code `CONNECTOR_NOT_REGISTERED` and the message "No connector is registered for capability '<action>' on this deployment. Nothing was executed." Before, it was a bare `500` with no code, and only the server log named the cause. Both SDKs already expose the code (`serverCode` in TypeScript, `server_code` in Python 1.1.6).
- Deployment artifacts found by following the production runbook on a fresh clone. The `Dockerfile` copied a package that no longer exists (`packages/receipt`) and skipped real workspaces, and the image did not contain `docs/site/parmana-handbook.pdf`, which the API needs at startup, so a container built from it could not have started. `scripts/apply-all-migrations.sql` was missing 7 of 30 migrations (including `execution_audit_events` and `policies`) and carried outdated text for others. It is now generated from `supabase/migrations/` with `npm run generate:migration-bundle`, and a test fails when it drifts. The runbook and the policy governance guide now say that proposing a policy change also needs a `USER` (human) key, because a service key is refused with `403 NON_HUMAN_CALLER_DENIED`.
- TypeScript SDK 1.1.6 and Python SDK 1.1.6 (both published on 2026-09-20, so both SDKs now share one version). TypeScript: the client builds a default `HttpTransport` from its own configuration when `transport` is omitted, so `timeout`, `retryPolicy` and `apiKey` apply with no extra wiring (1.1.5 and earlier threw `Transport is required.`), and `userAgent` is now sent as the `User-Agent` header. Python: `InternalServerError` now carries the server's code on `server_code`, so you can tell `SIGNING_UNAVAILABLE` from `EXECUTION_RECORD_INCOMPLETE`. The Python client docstring now lists 429 among retried statuses.
- TypeScript SDK 1.1.3 (published to npm on 2026-09-20): `InternalServerError` now carries the
  Runtime's own `code` on `serverCode`. Use it to tell `SIGNING_UNAVAILABLE` (503, nothing was executed, retry
  later with a new `businessTransactionId`) from `EXECUTION_RECORD_INCOMPLETE` (500, the action was released,
  do not retry as a new transaction). The SDK never auto retries `POST /execute`, so nothing is retried for you.

## 2026-09-11

**Added**

- Standalone offline signature verifiers with no network/disk dependency, TypeScript
  (`OfflineVerifier`) and Python (`offline_verifier.py`), cross-verified against each other.
- Public-key discovery: `GET /keys/:keyId` and `GET /.well-known/jwks.json`.
- Verification-key rotation support (`PARMANA_VERIFICATION_KEY_ID`, a rotation script), so a
  key can be rotated without breaking verification of records signed under the old key.
- Optional `HYBRID_SIGNATURE_REQUIRED` policy flag: an opted-in deployment now detects a
  stripped post-quantum signature on a record that should have one.

**Fixed**

- A production deployment with real caller authentication surfaced a database constraint gap:
  successful authenticated requests could fail closed with a `503` before policy ever ran.
  Fixed via a migration.
- `FileKeyProvider` reported the wrong signature algorithm for any key other than the default.

## 2026-09-10

**Added**

- `PostgresRateLimitStore`: `/execute` rate limiting is now durable and fleet-wide when
  `DATABASE_URL` is configured (previously in-process only).
- `GET /trust-records`: bulk, paginated export of full signed Execution Trust Records.
- Structured, level-gated logging (`createLogger`/`getLogger`).
- `npm run loadtest`: a load-testing script for `POST /execute`.

**Fixed**

- A misconfigured KMS/HSM key provider (`KEY_PROVIDER=aws-kms` etc.) now fails closed at
  startup instead of silently falling back to storing keys on disk.
- `GET /ready` now reports `authDisabled` explicitly in its JSON response.
- The Gateway's identity is now configurable (`PARMANA_GATEWAY_ID`) instead of hardcoded.
- A long-lived HubSpot credential with no rotation in 90 days now triggers a startup warning.

## 2026-09-09

**Added**

- `PolicyValidator.findRuleConflicts()`: flags policy rules whose conditions can both be true
  at once, advisory only, verified against every shipped policy with zero false positives.

**Fixed**

- Policy validation now fails closed on any rule-referenced fact with no `boundSignals`
  binding, instead of a load-time warning nobody would see. All shipped policies updated.
- `TenantKeyResolver`: Execution Authorizations now sign under a per-tenant key when one is
  provisioned, instead of always the shared default key.

**Changed**

## A note on terminology in older commits

Commit messages from before 2026-08 sometimes use "Execution Governance" as an architecture
name. The current, public-facing language avoids that term; if you find it in old commit
history, it refers to what this site now calls Policy Governance and the Execution Gateway,
not a separate product.
